# دیتالاگر UART برای AI-Thinker ESP32-CAM — نسخهٔ 0.1

این پروژه مخصوص برد کلاسیک AI-Thinker ESP32-CAM است، نه ESP32-S3-CAM یا بردهای دارای پایه‌بندی متفاوت. در صورت تفاوت برد، پیش از اتصال باید pinout بررسی شود. برنامهٔ دوربین قبلی برد با پروگرام این پروژه جایگزین می‌شود؛ قبل از آن از پروژهٔ قبلی نسخهٔ پشتیبان بگیرید.

## هدف

دریافت بایت‌های UART0 ردیاب G500 از GPIO43 با سرعت 115200 و ذخیرهٔ عین بایت‌ها در microSD. دوربین، Wi-Fi و Bluetooth راه‌اندازی نمی‌شوند. برنامهٔ ردیاب نیاز به تغییر جدید ندارد؛ همان print_str/print_string اصلاح‌شده با puts کافی است.

## فایل‌ها

- `platformio.ini`: انتخاب برد و چارچوب Arduino.
- `src/main.cpp`: برنامهٔ دیتالاگر به زبان C++؛ این کد Rust نیست.
- `README.md`: مراحل اجرا و محدودیت‌ها.

پوشه را مثلاً در `/home/prh/esp32cam-uart-logger` قرار دهید. مسیر فایل اصلی در این حالت `/home/prh/esp32cam-uart-logger/src/main.cpp` است. این یک پروژهٔ مستقل از `/home/prh/avl` است و داخل firmware ردیاب کپی نمی‌شود.

## مرحلهٔ ۱: وسایل

- برد AI-Thinker ESP32-CAM سالم، با اسلات microSD داخلی.
- کارت microSD با فایل‌سیستم FAT32؛ برای آزمایش اولیه کارت 8 تا 32 گیگابایتی مناسب است. فرمت‌کردن محتوا را پاک می‌کند؛ ابتدا از فایل‌های موجود پشتیبان بگیرید. کد خودکار کارت را فرمت نمی‌کند.
- تغذیهٔ 5V رگوله‌شدهٔ پایدار برای پایهٔ 5V برد؛ از برق خودرو به‌صورت مستقیم استفاده نکنید. منبع 5V با ظرفیت حدود 1A برای شروع در نظر بگیرید.
- CH340 با سیگنال UART سازگار با 3.3V برای پروگرام/مشاهدهٔ وضعیت.
- سیم‌های کوتاه و زمین مشترک.

## مرحلهٔ ۲: نصب پروژه در VS Code

1. افزونهٔ PlatformIO IDE را نصب/فعال کنید.
2. ZIP را استخراج کنید.
3. پوشه‌ای را باز کنید که `platformio.ini` در آن است.
4. اجازه دهید PlatformIO بسته‌های موردنیاز را نصب کند.
5. دکمهٔ Build را بزنید یا در PlatformIO Terminal اجرا کنید:

```bash
pio run
```

این محیط مستقل از کانتینر Rust پروژهٔ AVL است. `platform = espressif32` نسخهٔ ثابتی را قفل نمی‌کند؛ پس از build موفق برای بازتولید دقیق، نسخه‌های نصب‌شده را ثبت و سپس platform را روی نسخهٔ تأییدشده pin کنید. نسخهٔ اولیه در محیط تهیهٔ فایل با کامپایلر ESP32 کامپایل نشده است؛ اولین build کاربر مرحلهٔ تأیید سازگاری است.

## مرحلهٔ ۳: پروگرام ESP32-CAM

برای پروگرام، ردیاب به GPIO3 وصل نباشد.

| مبدل | ESP32-CAM |
| --- | --- |
| TX با منطق 3.3V | U0R / GPIO3 |
| RX | U0T / GPIO1 |
| GND | GND |

برد از 5V مناسب تغذیه می‌شود. پایهٔ 5V تغذیه است و GPIOها 5V tolerant نیستند. اگر منبع تغذیه جدا دارید، خروجی تغذیهٔ دو منبع را به هم متصل نکنید؛ زمین باید مشترک باشد.

1. در حالت خاموش GPIO0 را به GND وصل کنید.
2. برد را روشن/ریست کنید تا وارد حالت پروگرام شود.
3. Upload را بزنید یا `pio run -t upload` اجرا کنید.
4. پس از پایان، برد را خاموش کنید.
5. اتصال GPIO0 به GND را بردارید.
6. کارت را در حالت خاموش قرار دهید و برد را روشن کنید.

در صورت مشکل پروگرام، ابتدا بدون کارت تلاش کنید و کارت را پس از خاموش‌کردن برای اجرای عادی قرار دهید. GPIO0 به GND نباید برای اجرای عادی باقی بماند.

## مرحلهٔ ۴: ابتدا فقط SD را تست کنید

فعلاً ردیاب وصل نباشد. مانیتور را با 115200 و 8N1 باز کنید:

```bash
pio device monitor -b 115200
```

باید پیام‌هایی شبیه این ببینید:

```text
[LOGGER] BOOT: ESP32-CAM UART-to-SD v0.1
[LOGGER] FILE=/logs/log_000001.txt
[LOGGER] READY - start the tracker now
[LOGGER] rx=0 written=0 queue_drop=0 sd_drop=0 queued=0 sd=OK
```

در صورت `FATAL` ادامه ندهید. برنامه روی خطای راه‌اندازی متوقف می‌ماند؛ READY صادر نمی‌کند.

| خطا | موارد بررسی |
| --- | --- |
| SD mount failed | کارت، FAT32، تماس اسلات، تغذیه، مدل صحیح برد |
| Cannot create /logs | فضای کارت، خرابی فایل‌سیستم یا وجود فایل معمولی با نام logs |
| Cannot create a new log file | فضای کارت و قابلیت نوشتن |
| UART RX buffer / Queue allocation failed | تخصیص RAM؛ این نسخه بدون دوربین و شبکه اجرا شود |

## مرحلهٔ ۵: تست کوتاه با CH340، بدون ردیاب

وقتی READY دیده شد، از Serial Monitor یک خط مثل `LOGGER TEST 123` با پایان خط بفرستید. چون TX مبدل به GPIO3 وصل است، این متن ورودی دیتالاگر می‌شود. بعد از چند ثانیه `rx` و `written` باید افزایش پیدا کنند. پیام‌های وضعیت LOGGER روی GPIO1 هستند و به‌صورت داخلی در فایل لاگ نوشته نمی‌شوند.

برای پایان تست، ارسال را متوقف کنید؛ صبر کنید صف و بافر تخلیه شوند و written در پیام‌های متوالی ثابت بماند و با rx تطابق داشته باشد (در صورت نبود افت داده). چند ثانیه برای flush دوره‌ای فرصت بدهید، برد را خاموش کنید و بعد کارت را خارج کنید. این نسخه فرمان توقف امن ندارد و این روش تضمین قطع برق اتمیک نیست.

فایل `/logs/log_000001.txt` را در کامپیوتر باز کنید. باید متن آزمایشی داخل آن باشد. پس از هر بوت، فایل جدید ساخته می‌شود؛ شمارهٔ واقعی ممکن است متفاوت باشد.

## مرحلهٔ ۶: اتصال به ردیاب

در حالت خاموش، سیم TX مبدل را از GPIO3 برد دیتالاگر جدا کنید. سپس:

| ردیاب G500 | دیتالاگر ESP32-CAM |
| --- | --- |
| GPIO43، TX لاگ با سطح 3.3V | GPIO3 / U0R |
| GND | GND |

برای مشاهدهٔ وضعیت دیتالاگر، RX مبدل می‌تواند به GPIO1 / U0T برد ESP32-CAM وصل بماند؛ زمین مبدل مشترک باشد. **TX مبدل نباید هم‌زمان با TX ردیاب به GPIO3 وصل باشد.** روی یک ورودی دو خروجی فعال را به هم وصل نکنید.

ESP32-CAM اول روشن شود؛ پس از READY، ردیاب روشن شود تا لاگ‌های بوت هم ثبت شوند. داده‌ای که قبل از آماده‌بودن دیتالاگر ارسال شده باشد تضمین ثبت ندارد. از اتصال TTL به خروجی RS232 کانکتور DMS بدون بررسی سطح سیگنال خودداری کنید؛ اتصال این پروژه مستقیم به GPIO43 است.

## مرحلهٔ ۷: روند نرم‌افزار

1. `Serial.setRxBufferSize(16384)` پیش از `Serial.begin` درخواست بافر RX می‌دهد.
2. UART0 روی GPIO3 برای RX و GPIO1 برای خروجی تشخیصی با 115200/8N1 تنظیم می‌شود.
3. `SD_MMC.begin("/sdcard", true, false)` کارت را در حالت 1-bit و بدون فرمت خودکار mount می‌کند.
4. پوشهٔ `/logs` و اولین نام آزاد `log_000001.txt` تا `log_999999.txt` انتخاب می‌شود.
5. یک task جدا روی core 0 فقط UART را می‌خواند و بسته‌های حداکثر 256 بایتی در صف می‌گذارد.
6. loop اصلی تنها نویسندهٔ فایل است؛ بسته‌ها را تا 4096 بایت جمع می‌کند و دسته‌ای می‌نویسد.
7. هر حدود یک ثانیه، بافر نیمه‌پر هم نوشته و flush درخواست می‌شود.
8. هر پنج ثانیه شمارنده‌ها روی GPIO1 چاپ می‌شوند.
9. در مرز 16 MiB فایل جدید ساخته می‌شود. مرز فایل لزوماً مرز خط متن نیست؛ ممکن است یک خط بین دو فایل تقسیم شود. با الحاق فایل‌ها به ترتیب شماره، ترتیب بایت‌ها حفظ می‌شود، به شرط نبود افت داده.

## معنی شمارنده‌ها

| مقدار | معنی |
| --- | --- |
| rx | بایت‌هایی که task واقعاً از API سریال خوانده؛ شمارندهٔ 32 بیتی و قابل wrap |
| written | بایت‌هایی که File.write موفق گزارش کرده؛ 64 بیتی |
| queue_drop | بایت‌های خوانده‌شده‌ای که به علت پرشدن صف کنار گذاشته شده‌اند |
| sd_drop | بایت‌هایی که پس از خطای SD یا شکست نوشتن کنار گذاشته شده‌اند |
| queued | تعداد بسته‌های حاضر در صف؛ نه تعداد بایت‌ها |
| sd=OK | خطای قابل تشخیص mount/open/write مشاهده نشده؛ تضمین صحت فیزیکی همهٔ داده‌ها نیست |

در هنگام دریافت، rx می‌تواند موقتاً از written بزرگ‌تر باشد، چون داده در صف یا بافر دسته‌ای است. queue_drop=0 اثبات عدم اتلاف در سطح سخت‌افزار UART نیست؛ این نسخه رویدادهای UART FIFO overflow یا framing error را جداگانه نمی‌شمارد. flush در این API خروجی نتیجهٔ قابل بررسی ندارد، پس شکست‌های احتمالی تخلیهٔ نهایی به‌طور کامل شناسایی نمی‌شوند.

## مدیریت حافظه و سرعت

در 115200 و 8N1 سقف نظری داده 11520 بایت در ثانیه است. ظرفیت RX درخواستی 16 KiB است؛ صف 64 بستهٔ حداکثر 256 بایتی دارد و بافر نوشتن 4 KiB است. بسته‌های نیمه‌پر هم یک خانهٔ کامل صف می‌گیرند؛ بنابراین ظرفیت مؤثر صف همیشه 16 KiB داده نیست. این معماری تأخیر SD را تا حدی جذب می‌کند، ولی تضمین عدم اتلاف نیست. در جریان کاملاً پر، حجم نزدیک 41.5 MB در ساعت است؛ نرخ واقعی معمولاً کمتر است.

از String برای جمع‌کردن بی‌حدومرز خطوط استفاده نشده است. بایت‌های ورودی بدون تفسیر ذخیره می‌شوند؛ UTF-8 فارسی و پایان‌خط‌ها دست‌نخورده می‌مانند. اگر لاگ شامل ANSI یا بایت باینری باشد، همان‌ها نیز داخل txt قرار می‌گیرند. پسوند txt دادهٔ باینری را به متن تبدیل نمی‌کند.

## محدودیت‌های نسخهٔ اول

- برای تست اولیه و توسعه است؛ تست میدانی و تضمین عدم اتلاف ندارد.
- خطای نوشتن/پرشدن کارت، ثبت را متوقف می‌کند؛ دریافت و گزارش افت ادامه دارد. کارت را در حالت روشن تعویض نکنید. برای بازیابی، پس از رفع مشکل ریست کنید.
- فایل‌های قبلی خودکار حذف یا بازنویسی نمی‌شوند؛ مدیریت پرشدن کارت هنوز دستی است.
- فرمان توقف امن، RTC، زمان واقعی افزوده‌شده، شبکه و بازیابی قطع برق پیاده‌سازی نشده‌اند.
- flush هر ثانیه به معنی تضمین از دست رفتن حداکثر یک ثانیه نیست؛ دادهٔ صف، تأخیر SD و فایل‌سیستم هم دخیل‌اند.
- کارت حافظه و فایل FAT ممکن است در قطع برق ناگهانی آسیب ببینند. برای نسخهٔ عملی دکمه/فرمان توقف امن و فرصت حفظ تغذیه باید طراحی شود.
- انتخاب پایهٔ دکمه را بدون بررسی نکنید؛ GPIO13 و GPIO12 با کارت و GPIO0 با بوت/دوربین ارتباط دارند.
- GPIO4 چراغ فلش است و در کد خاموش نگه داشته شده؛ SD در حالت 1-bit از D1 به‌عنوان خط داده استفاده نمی‌کند.

## برنامهٔ ادامهٔ توسعه

پس از اثبات mount و ثبت خط آزمایشی: اتصال به ردیاب، آزمایش جریان طولانی با شمارهٔ ترتیبی، بررسی افت و ترتیب بایت‌ها، افزودن شمارندهٔ خطاهای UART، توقف امن، و سپس سیاست پرشدن کارت. برای کنترل صحت، مولد تست می‌تواند خطوط شماره‌دار بفرستد؛ فایل ذخیره‌شده باید بدون فاصله در شماره‌ها باشد. تست سخت‌افزاری در این محیط انجام نشده است.
